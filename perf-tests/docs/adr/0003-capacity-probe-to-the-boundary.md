# 容量上限用加压探针测，每档一个子进程

宿主编排层没有 `max_apps` 常量，同时常驻的真实上限由 RSS / 调度决定。固定档
（S1：4/8/16/32）只能回答「支撑数够不够」，回答不了「最多能到多少」——32 档
全绿时报告里只有「达到探针上限」，看起来像上限本身就是 32。要给出上限，必须
让测量**自己去找边界**。

## 决定

- **加压到不可用为止**：S4 从 4 起翻倍（4/8/16/32/…/`--max-apps`），某一档
  不可用后停止，再在 `(最大可用, 首个不可用]` 区间二分到相邻整数。
- **每档一个子进程**（`--capacity-probe <N>`）：子进程装配 N 个实例、全量激活、
  逐实例 `bench.ping`，把 `RSS / activated / 激活耗时 / ping 样本 / 失败原因`
  写成标记行回给父进程，然后退出。
- **判定顺序固定**：装配 → 激活 → 回执 → RSS → 单命令中位数。先报「跑不起来」
  （装配 / 激活 / 回执失败、子进程崩溃），再报「跑得慢」（RSS 或延迟超限），
  避免把激活失败误读成性能退化。
- **边界归因写进报告**：首个不可用档的实测原因（`assemble-failed` /
  `activation-failed` / `ping-failed` / `rss-ceiling` / `latency` /
  `probe-crashed`）连同证据一起落测点；压到 `--max-apps` 仍全绿记
  `probe-limit`，明确「未触底」而不是当成上限。
- **上限不设门禁**：只有「最大可用数 < 16（交付支撑下限）」才红。上限本身随
  机器 / 内存波动，把它变成回归线会让基准因机器差异变红，违背数量级门禁口径。
- **二分依赖单调性**：RSS 与激活成本随 N 单调，命令延迟有抖动；因此每档实测
  都进报告，结论只取实测档位，二分只用来缩小搜索区间。

## 为什么不是进程内逐档装配

`PluginHost::init_message_bus` 把 `Arc<PluginHost>` 的克隆装进 message bus 的
dispatcher 槽：host → bus → dispatcher(host)，构成 `Arc` 环。进程内停用并丢弃
宿主后引用计数不为零，实例不会被释放。实测同一档位在第二轮比第一轮高几十 MiB，
容量判定会系统性偏小（曾把 17 个实例误判成 200 MiB 上限下的不可用档，实际
约 160 MiB）。子进程让每档都是「N 个应用同时常驻」的干净整进程口径，也顺带
隔离高档位的 trap / OOM——父进程只看到没有回执，记 `probe-crashed`。

代价是每档重复进程启动与引擎初始化（秒级），因此 S4 不进冒烟子集，只在
`--full` 或精确点名（`--group S4`）时运行。

## 为什么不直接复制真实应用

真实应用清单里 `contributes.commands` 与 `api` 是全局唯一的：同一应用复制 N 份
属主，注册表会 fail-closed 拒绝（同名 api 多属主、重复命令 id）。要测真实应用的
容量边界，得先做命令 / api / 数据目录的命名空间隔离——这是产品面的改动，不是
测量侧能绕过的。当前口径：

- S4 测**宿主 wasm 实例容量**（合成夹具，`S4.rss-per-app` 是该夹具的边际内存）；
- R1 测**真实应用内存画像**：`R1.rss-delta.<app>` 是顺序激活增量（基准取装配完成、
  激活开始前的 RSS），`R1.real-app-estimate` = 可用内存 / 单应用增量中位数，
  明确标注为估算。

## Consequences

- 报告里会多出 `S4.step-<n>.*` 明细测点；`--compare` 对齐时以 `S4.max-apps`
  与 `S4.first-bad` 为主，明细用于解释边界落在哪一档。
- 子进程继承父进程的构建档位（debug 构建由父进程的 `--allow-debug` 放行），
  临时目录与夹具产物沿用同一套 resolver，不额外配置环境。
- 真实应用容量仍是估算，不得引用成「实测可同时运行 K 个真实应用」；要做实测，
  先落命名空间隔离（另立票据）。
